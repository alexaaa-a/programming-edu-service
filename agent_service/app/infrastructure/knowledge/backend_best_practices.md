# Backend Best Practices — универсальная памятка для code review

Документ описывает language-agnostic принципы качества бэкенда: API-контракты, безопасность, валидация, обработка ошибок, транзакционность, конкуррентность, наблюдаемость и тестируемость.

Цель — давать единый “скелет” для review независимо от языка/фреймворка.

## 0. Мини-workflow при ревью бэкенда
1. **Контракт API**: запрос/ответ, схемы, статусы, идемпотентность.
2. **Валидация**: входные данные, типы, ограничения, нормализация.
3. **Ошибки**: стратегия (что возвращаем), логирование с контекстом, отсутствие silent failures.
4. **Побочные эффекты**: БД/сеть/файлы — где начинается и где заканчивается операция.
5. **Конкуррентность**: гонки, блокировки, очереди, порядок операций.
6. **Безопасность**: аутентификация/авторизация, защита от инъекций, rate limiting.
7. **Наблюдаемость**: логи, метрики, трассировка, корреляция.
8. **Тесты**: unit/integration/e2e, контрактные тесты на API.

## 1. API-контракты и схемы данных
Проверь:
- Ответы предсказуемы: нет “иногда одно поле, иногда другое”.
- Стабильность форматов (даты, числа, enum/строки).
- Корректность HTTP/доменных статусов и сообщений.
- Версионирование: если схема меняется, как это поддерживается?

Практика:
- Валидируйте request и response согласно схеме до бизнес-логики.
- Для сложных интеграций фиксируйте контракт (OpenAPI/JSON Schema/DTO).

## 2. Валидация и нормализация входа
Проверь:
- Валидация обязательных полей и бизнес-ограничений (len, ranges, regex, allowed values).
- Контроль типов: например, “число приходит как строка” или “bool приходит как 0/1”.
- Отказ безопасный: неправильный ввод не приводит к несанкционированным действиям.

## 3. Обработка ошибок: контекст + воспроизводимость
Красные флаги:
- `except: pass`,
- `except Exception` без классификации,
- ошибки “проглатываются” и клиент получает generic error без деталей (но детали не потеряны в логах).

Хорошо:
- error response содержит понятный код/сообщение,
- логи содержат trace id/correlation id, параметры (без секретов), endpoint и причину.

## 4. Транзакционность и целостность данных
Проверь:
- Когда нужна транзакция и какие границы?
- Есть ли защита от частичных обновлений (half-written state)?
- Миграции БД: обратимость/совместимость версий.

Если есть очереди/события:
- обработчик устойчив к повторной доставке (at-least-once),
- операции идемпотентны или имеют dedup ключи.

## 5. Конкуррентность, порядок операций и гонки
Проверь:
- Race conditions: несколько запросов меняют одни и те же ресурсы.
- Блокировки/конкурентные коллекции: корректность при высокой нагрузке.
- Cancellation/timeouts: зависание сетевых вызовов исключено.

## 6. Безопасность (OWASP-like, без привязки к стеку)
Проверь:
- Аутентификация и авторизация: проверяется ли право на действие?
- Защита от инъекций (SQL/NoSQL/command/template) через параметризованные запросы и safe builders.
- XSS/CSRF: на уровне взаимодействия и политик.
- Секреты: не логируются и не уходят в ответы.
- Rate limiting / throttling: защита от brute-force и DoS.

## 7. Наблюдаемость и SRE-практики
Проверь:
- единый формат логов (json) и корреляция по trace/request id,
- метрики (latency, error rates, throughput) без “лишних” тегов,
- трассировка при распределённых вызовах.

## 8. Производительность и работа с ресурсами
Проверь:
- N+1 запросы и неэффективные выборки.
- Кэширование: где оно корректно, где может сломать консистентность?
- Пулы соединений/таймауты.

## 9. Тестируемость и контрактные проверки
Проверь:
- unit тесты на бизнес-логику,
- integration тесты на репозитории/контуры данных,
- контрактные тесты на API схемы/ошибки.

## Мини-анти-чеклист
- Возврат “дефолтов” вместо ошибок без причины.
- Ошибки без контекста в логах.
- Невалидируемые данные до бизнес-логики.
- Нет таймаутов у сетевых вызовов.
- Нестабильные контракты ответа (поля меняются без версионирования).

## Универсальные вопросы для review
- Можно ли гарантировать воспроизводимость ошибки (что логируется, где trace id)?
- Что будет при повторном доставлении события?
- Где границы транзакции/атомарности?
- Как система ведет себя при частичных сбоях внешних сервисов?
