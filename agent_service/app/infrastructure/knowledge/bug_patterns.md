# Типичные паттерны багов — что искать на code review

Этот документ — “карта местности” для поиска дефектов на code review.
Его цель — помочь быстро выявлять баги по категориям: от граничных случаев (edge cases) и ошибок парсинга до проблем асинхронности и “протечки” состояния между запросами.

## 0. Как пользоваться (практический сценарий)
1. Прочитай контекст: что получает функция/метод (вход), что возвращает (выход), какие есть побочные эффекты (IO, изменения БД, внешние сервисы).
2. Выпиши предположения (assumptions): формат данных, обязательность ключей, наличие `await`, порядок событий, наличие ресурсов/таймаутов.
3. Для каждого предположения задай проверку:
   - Что будет при пустом/неожиданном/частично валидном вводе?
   - Где контур обработки ошибок? Как сохраняется причина сбоя?
   - Есть ли риски гонок/конкурентности?
4. По итогам предложи:
   - исправление (конкретная правка),
   - тесты/валидацию,
   - и/или дополнительные guardrails (валидация схем, логирование, таймауты).

## 1. Граничные случаи (edge cases) и валидация
Часто баг появляется не в “обычном” сценарии, а в неожиданном углу.

Проверь:
- Пустые строки/списки/массивы: `""`, `[]`, `None`.
- Отсутствующие/лишние поля: непредусмотренные структуры, другой формат вложенности.
- Граничные значения чисел:
  - 0, отрицательные значения,
  - min/max, переполнения/underflow,
  - float-округления и потерю точности.
- Несовпадение форматов:
  - даты в разных форматах/часовых зонах,
  - числа с разделителями и разной локалью,
  - чувствительность к регистру.

Сигналы:
- `KeyError`, `TypeError`, `ValueError` на краях.
- “Вроде работает”, но в предельных значениях ломается или возвращает неверный результат.

## 2. Ошибки с асинхронностью и отменой
Асинхронный код добавляет новые классы ошибок: неправильный порядок ожидания, проблемы отмены и гонки.

Красные флаги:
- Забытый `await` (получается coroutine, но код продолжает работать “как будто”).
- Ожидание/неожидание результата не соответствует модели (например, “параллельное” должно быть `gather`, а сделано последовательно).
- Использование общего mutable-состояния между корутинами без защиты.
- Отмена (`cancel`) обработана некорректно:
  - не перехватывается `CancelledError`,
  - не делается cleanup (закрытие ресурсов),
  - отмена “проглатывается” и операция зависает/получает неожиданные статусы.

Что проверить:
- Есть ли гарантии освобождения ресурсов при отмене?
- Создаются ли “вечные” задачи через `create_task` без отмены на shutdown?
- Нет ли гонок между чтением/записью shared state?

## 3. Скрытые ошибки обработки исключений
Проблема обычно не в наличии `try/except`, а в стратегии:
 - молчаливая обработка,
 - потеря контекста,
 - возвращение “дефолта” вместо явной ошибки.

Красные флаги:
- `except Exception: return default` без логирования.
- `except: pass` — почти всегда приводит к “тихим” поломкам.
- Проглатывание исключений без причины/контекста (нет trace/log/корреляции).
- Широкие `except Exception` без классификации.

Хороший сигнал:
- есть логирование с контекстом (что именно было не так),
- ошибка либо пробрасывается,
- либо преобразуется в понятный доменный результат/ошибку,
- либо аккуратно компенсируется, сохраняя инварианты.

## 4. Непредсказуемость данных и форматов
Если данные не валидируются, ошибки часто проявляются “позже”, когда уже труднее понять первопричину.

Проверь:
- Есть ли явная валидация входных данных (типы/схемы)?
- Даны ли контракты для “плохих” данных: что делаем при отсутствии ключей, неверном формате, пустом значении?
- Есть ли проверка валидности JSON/структуры до использования полей?

Типичные проблемы:
- предположение о наличии ключей,
- использование значений “как есть” без нормализации,
- смешивание типов (например, где ожидали `int`, внезапно приходит `str`).

## 5. Ошибки парсинга/сериализации и форматирование (JSON, даты, строки)
Эта категория включает баги на стыке “данные <-> формат <-> объект”.

Частые сценарии:
- Неполные/невалидные JSON: ответ LLM или внешний сервис иногда возвращает “почти JSON”.
- Баги при обработке code-block:
  - JSON в ```json ... ```,
  - лишний текст вокруг JSON,
  - неверные разделители/маркер языка.
- Ошибки преобразований дат:
  - разные часовые зоны,
  - неправильный парсер,
  - допущения о формате.

Что смотреть в коде:
- Есть ли robust parsing или попытка “вытащить { ... }”?
- Что происходит при частично валидном ответе?
- Не делаем ли слишком смелых `strip()`/`removeprefix()` без проверки границ?

## 6. Повторное использование состояния и “протечки”
Баги из серии “иногда работает” часто связаны с тем, что состояние неожиданно разделяется.

Проверь:
- Глобальные переменные/кэш, которые протекают между запросами.
- Изменяемые атрибуты класса вместо локальных/инстанс-переменных.
- Мутация объектов, которые переиспользуются (например, списки, словари, кеш внутри singleton).
- Кэширование без корректного invalidation (или с неверным ключом).

Сигналы:
- зависимость результата от порядка запросов,
- “фантомные” баги, которые исчезают после перезапуска.

## 7. Ресурсы и IO: таймауты, закрытие, обработка ошибок
Even “простые” запросы к внешним ресурсам часто ломаются в условиях плохой сети/медленного ответа.

Красные флаги:
- Отсутствие таймаутов у запросов.
- Ресурсы не закрываются (клиенты, сессии, файловые дескрипторы).
- Нет retries/backoff или они без ограничений (может превратиться в бесконечную нагрузку).

Проверь:
- Где создаётся ресурс и где точно освобождается?
- Есть ли обработка конкретных ошибок IO?
- Есть ли ограничения по времени и размеру ответа?

## 8. Мини-чеклист при поиске багов
- Есть ли явная валидация входа?
- Что будет при пустом/неожиданном/частично валидном вводе?
- Где могут быть исключения и что с ними делают (логирование + стратегия)?
- Есть ли проблемы с `await`, отменой, параллелизмом?
- Нет ли “магических” предположений о формате данных/ответов?
- Нет ли state-протечек: кэш, глобальные переменные, изменяемые атрибуты класса?
- Есть ли таймауты и корректное освобождение ресурсов?

## 9. Анти-чеклист (что точно стоит избегать)
- `except: pass` и `except Exception` без логирования.
- Использование результата функции/корутины без явного `await`.
- Непроверенный JSON/тип без guardrails.
- Глобальные shared objects без инвариантов и без защиты.
- Кэширование “навсегда” без invalidation/TTL (если не доказано обратное).
