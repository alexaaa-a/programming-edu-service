# Full-Stack Best Practices — универсальная памятка для code review

Документ объединяет best practices для полного стека: frontend + backend + интеграции + наблюдаемость + доставка/релизы.
Подходит для любых языков программирования и фреймворков.

Фокус — на end-to-end качестве: как данные проходят через интерфейсы, как ошибки представлены пользователю, как система измеряется и как поддерживается при изменениях.

## 0. End-to-End workflow при full-stack ревью
1. **Контракт**: запрос/ответ, схемы, статусы, поля, форматы.
2. **Сценарии UX**: загрузка/пусто/ошибка/успех, повторение действия, отмена.
3. **Ошибки и диагностика**:
   - как ошибка доходит до UI,
   - как она логируется на backend,
   - есть ли корреляция по trace id.
4. **Согласованность данных**:
   - как обновляются state на фронте после мутаций,
   - как backend обеспечивает консистентность и идемпотентность.
5. **Наблюдаемость**: логи/метрики/трейсы на обоих концах и единая корреляция.
6. **Безопасность**: аутентификация, авторизация, защищенность каналов.
7. **Стабильность изменений**:
   - как схема/контракт обновляется без “сломов”,
   - как обеспечивается обратная совместимость.

## 1. Контракт и совместимость схем
Проверь:
- Схемы request/response синхронизированы и версионированы.
- Форматы унифицированы (даты, enum, суммы/валюта/точность).
- Обратная/прямая совместимость продумана (например, добавление полей vs изменение семантики).

Альтернатива:
- если разные команды поддерживают контракт — используйте contract-first (OpenAPI/Schema-first).

## 2. Протокол ошибок и UX-реакция
Проверь:
- backend возвращает предсказуемые ошибки (код/сообщение/детали там, где нужно),
- frontend показывает пользователю осмысленные сообщения,
- ошибки не “переупаковываются” без контекста.

Важно:
- диагностика (trace id) доступна в логах, а не обязательно пользователю,
- пользователю — понятный результат и следующий шаг.

## 3. Конкурентность и консистентность между слоями
Проверь:
- Нет гонок между фронтом и бэком: повторный запрос не приводит к двойной записи.
- Идемпотентность мутаций продумана (ключи идемпотентности/dedup).
- UI обновляет state корректно (после подтверждения или с безопасным rollback).

## 4. Observability across stack
Проверь:
- единый формат логов (желательно JSON),
- метрики отражают end-to-end: latency API, error rate, throughput, доля cache hits,
- трассировка позволяет связать запрос пользователя с downstream вызовами.

Корреляция:
- request/trace id должен проходить через цепочку “front → backend → внешние сервисы”.

## 5. Безопасность на стыках
Проверь:
- авторизация на backend (не только на frontend),
- защита от XSS/CSRF и корректные заголовки/политики,
- безопасная обработка пользовательского ввода и данных из внешних источников,
- контроль утечек в логах/ответах.

## 6. Производительность и UX под нагрузкой
Проверь:
- стратегия пагинации/виртуализации и ограничение payload,
- кеширование: где оно уместно и как инвалидируется,
- fallback поведение при degradations (например, “показать старые данные” при временной недоступности).

## 7. CI/CD и стратегия релизов
Проверь:
- если меняются контракты — релиз не ломает старые версии клиентов,
- миграции данных совместимы с текущими и следующими версиями,
- feature flags позволяют безопасно включать изменения.

## 8. Мини-чеклист при full-stack review
- Контракт синхронизирован и совместим?
- Ошибки и сценарии UX покрыты?
- Идемпотентность/гонки учтены?
- Observability связана сквозь слои?
- Безопасность соблюдена на сервере?
- Тесты покрывают end-to-end критические сценарии?

## Anti-checklist
- “Работает у меня” без гарантии схем/ошибок/краевых случаев.
- Изменения контракта без версионирования.
- Ошибки без контекста и без диагностики.
- Мутации без идемпотентности при возможной повторной доставке.
