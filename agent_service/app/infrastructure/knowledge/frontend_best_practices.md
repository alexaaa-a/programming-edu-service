# Frontend Best Practices — универсальная памятка для code review

Документ описывает language-agnostic принципы качества фронтенда: читаемость UI-кода, корректная работа с состоянием и сетью, безопасность, доступность и производительность.

Цель — помогать быстро находить дефекты и инженерные риски на ревью, независимо от фреймворка/языка.

## 0. Мини-workflow при ревью фронтенда
1. **Поток данных**: от события пользователя до изменения state и до запроса/ответа.
2. **Контракты**: какие API/DTO ожидаются, где валидируются вход/выход.
3. **Ошибка и отмена**: что происходит при ошибках сети, 4xx/5xx, таймаутах и отмене запросов.
4. **UX-устойчивость**: загрузки, пустые состояния, ретраи, дедупликация действий.
5. **Безопасность и доступность**: XSS/CSRF, работа с фокусом, клавиатура, aria-атрибуты.
6. **Производительность**: лишние ререндеры, размер бандла, длинные списки, кеширование.

## 1. Архитектура компонентов и управляемость state
Проверь:
- Компоненты имеют чёткие границы ответственности: UI-рендеринг отдельно от логики данных/валидации.
- Состояние не дублируется без необходимости (источник правды — один).
- Нет “скрытого” глобального состояния/мутаторов, которые протекают между сессиями пользователей.
- Изменения state предсказуемы: нет гонок между несколькими async-операциями.

Типичные баг-паттерны:
- “Старый ответ” перезаписывает более новый запрос (race condition).
- Повторные клики создают несколько параллельных запросов без дедупликации.
- UI отображает значение до завершения валидации (optimistic update без guardrails).

## 2. Работа с сетью: загрузка, ошибки, отмена, ретраи
Проверь:
- Есть явные состояния: `loading`, `empty`, `error`, `success`.
- Ошибки не теряются: пользователь получает понятное сообщение, а в логах/мониторинге есть причина.
- Поддерживается отмена/игнорирование устаревших запросов при смене контекста.
- Таймауты и ограничения есть (запрос не зависает бесконечно).
- Ретраи применяются только там, где это безопасно (обычно GET/идемпотентные операции).

Практика:
- Для ретраев используйте backoff и ограничение числа попыток.
- Для POST/мутаций контролируйте идемпотентность на бэкенде или клиенте.

## 3. Валидация данных на клиенте
Проверь:
- Входные формы валидируются до отправки (минимум: обязательные поля, формат email/URL, длины).
- Нельзя полагаться на “идеальный” ввод: клиент проверяет и показывает ошибки.
- Ответ от API валидируется/нормализуется до использования в UI (особенно для сложных JSON).

Если схема ответа нарушена:
- UI деградирует безопасно (не падает, не ломает компоновку).
- ошибка логируется с контекстом (endpoint, session, correl-id).

## 4. Доступность (a11y) и UX-контуры
Проверь:
- Навигация с клавиатуры: фокус видим и логичен.
- Семантика: корректные роли/теги/aria там, где нужно.
- Контраст и читаемость.
- Ошибки форм читаемы: сообщения связаны с полями (aria-describedby/label).
- Для динамического контента есть уведомление пользователю (например, aria-live).

Красные флаги:
- интерактивные элементы без семантики (например, `div` как кнопку),
- скрытый фокус,
- “немые” ошибки (ошибка появилась, но пользователь не понял где).

## 5. Безопасность на фронтенде
Проверь:
- XSS: данные из API/пользователя экранируются или рендерятся как текст, а не как HTML.
- Учет URL-параметров: отсутствие инъекций через query/hash.
- CSRF-политики соответствуют способу авторизации.
- Не хранить секреты на клиенте; токены — только по безопасным принципам (например, httpOnly cookie, если применимо).

## 6. Производительность и эффективность рендеринга
Проверь:
- Не создаются новые обработчики/объекты без нужды (лишние ререндеры).
- Для больших списков используется виртуализация/пагинация.
- Memoization применяется осознанно (без “слепой” оптимизации).
- Изображения/ресурсы оптимизированы (форматы, lazy loading, размеры).
- Логику сортировки/фильтрации не выполняют на каждом рендере без мемоизации.

## 7. Протокол ошибок и трассируемость
Проверь:
- Единый формат ошибок для UI (код/сообщение/поля).
- Корреляция с бэкендом: request id / trace id прокидываются для отладки.
- Нет “немых” ошибок в консоли: всё должно быть либо пользователю, либо в мониторинг.

## 8. Мини-анти-чеклист
- `catch` без обработки (ошибка проглочена, UI завис).
- Optimistic UI без rollback/подтверждения.
- UI зависит от глобального изменяемого состояния без источника правды.
- Вставка HTML из внешних данных.
- Непредсказуемая загрузка из-за гонок async-операций.

## 9. Универсальные “шаблоны” вопросов на review
- Где гарантируется, что последняя операция побеждает?
- Что показывает UI при `timeout`, `429`, `500`?
- Что произойдет, если форма заполнена частично или API вернул неожиданный JSON?
- Можно ли повторить действие без побочных эффектов?
- Есть ли доступность для клавиатуры и screen reader?
