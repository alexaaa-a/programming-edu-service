# Чистый код (Clean Code) — практики для стабильного code review

Этот документ — шпаргалка для ревью кода: он помогает находить проблемы не только “в стиле”, но и в инженерных свойствах.
Фокус: читаемость, предсказуемость поведения, корректная обработка ошибок, ясные контракты и отсутствие скрытых дефектов.

## 0. Workflow: как применять Clean Code при ревью
1. Определи намерение: что делает код и какие инварианты он поддерживает?
2. Проверь контракты: вход/выход, типы, обязательность полей, предположения о данных.
3. Пройдись по “контуром ошибок” (что произойдёт при плохом вводе/ошибке внешнего IO/невалидных ответах?).
4. Только потом обсуждай формат/имена/композицию — чтобы не свести ревью к косметике.

## 1. Имена переменных, функций и классов
Имя должно объяснять назначение без чтения внутренностей.

Проверь:
- `tmp`, `data2`, `x`, `foo` — только для действительно локальных временных переменных на коротком участке.
- Имена отвечают на вопрос “что это?” и “зачем это?”.
- Избегай двусмысленностей: одно и то же слово используется для разных смыслов.
- Единообразие в стиле проекта (`snake_case`/`camelCase`), единый подход к сокращениям.

Критерий:
- Можно ли прочитать код сверху вниз и понять поток логики, опираясь на имена?

## 2. Функции должны быть маленькими и однонамеренными
Большая функция — часто индикатор размытых границ ответственности.

Проверь:
- функция понятна за 1–2 минуты чтения,
- нет “слипшихся” задач (валидация + вычисление + сериализация в одном месте),
- нет чрезмерной глубины вложенности — используй guard clauses/ранние возвраты,
- каждая функция имеет ограниченную причину для изменения (single responsibility / “правило одного изменения”).

Сигналы к рефакторингу:
- функция возвращает несколько типов без явной схемы,
- много ветвлений, которые покрывают разные сценарии домена,
- “магические” преобразования данных без объяснения причин.

## 3. Обработка ошибок и исключений
Чистый код не “глушит” ошибки: он либо восстанавливает инварианты, либо сообщает с контекстом.

Красные флаги:
- `except: pass`,
- `except Exception: return default` без логирования и причины,
- слишком широкий `except` без классификации,
- пропуск ошибок парсинга (например, JSON) без проверки инвариантов.

Хорошая практика:
- ловить конкретные исключения,
- добавлять контекст: какие входные данные/параметры привели к проблеме,
- либо пробрасывать дальше, либо преобразовывать в понятный доменный результат/ошибку.

## 4. DRY и “умные” абстракции
DRY полезен, но чрезмерные абстракции ухудшают чтение и мешают отладке.

Проверь:
- повторяется именно бизнес-логика, а не детали реализации цикла/форматирования,
- абстракция имеет понятные границы ответственности,
- компонент можно протестировать изолированно,
- использование абстракции читабельно: без скрытых “магий” внутри.

Если после абстракции стало сложнее понять поток — скорее всего, абстракция слишком умная.

## 5. Форматирование и стиль
Единообразный стиль ускоряет чтение и снижает вероятность ошибок.

Проверь:
- единый подход к форматированию внутри модуля,
- согласованная структура блоков (условия/циклы/обработчики ошибок),
- отсутствие “смешанного” стиля, который маскирует логические ошибки.

Важно:
- стиль не заменяет корректность, но помогает заметить проблемы быстрее.

## 6. Типы и контракты
Типизация — инструмент ясности и раннего обнаружения ошибок.

Проверь:
- типы для входа/выхода ключевых функций,
- минимизация `Any` там, где можно сужать контракт,
- проверка инвариантов до использования данных.

## 7. Комментарии
Комментарии нужны для объяснения “почему”, а не “что”.

Правило:
- если комментарий описывает очевидную строку — возможно, имя/структура требуют улучшения.

Хорошие комментарии отвечают:
- почему принято такое решение,
- какие компромиссы,
- какие ограничения/предположения.

## 8. Принцип “правило одного изменения”
Изменение бизнес-правила не должно затрагивать весь проект.

Проверь:
- связность кода высокая, зависимости управляемы,
- границы ответственности понятны,
- нет “всем всё нужно” — слишком жёсткая связность увеличивает стоимость изменений.

## Мини-чеклист при review
- Имена ясные и доменно точные?
- Функции маленькие и однонамеренные?
- Есть ли контекстная обработка ошибок (нет `pass`/тишины)?
- Контракты и схемы понятны и валидируются?
- Границы ответственности и причина изменений локальны?

## Anti-checklist (что чаще всего ломает качество)
- проглатывание ошибок (`except: pass`, “тихие” дефолты),
- “умные” абстракции без тестируемости и объяснимости,
- отсутствие явных контрактов (любой вход, любой выход),
- огромные функции и глубоко вложенные блоки, которые трудно проследить.
